# 业务门自动验收

> 对照 `../../templates/门禁卡-业务门.md` 逐项收集证据并判定通过/不通过。

---

## 过门禁标准（12 项必须满足的指标）

1. **P0 功能完成**：功能清单中 P0 全部交付；P1 / P2 写明"未做 / 延后"原因。
2. **每轮验收证据**：按一轮一验收推进，每轮有执行命令 + 输出。
3. **测试六步法**：每个模块走 `testing-strategy`，含假测试与过度测试自查。
4. **接口自动化 + 端到端**：核心接口覆盖成功 / 参数错误 / 未登录 / 无权限 / 访问他人数据 / 资源不存在；核心用户流程真实走通，给页面结果和数据库结果。
5. **安全 5 关**：身份认证 / 权限控制 / 输入校验 / 数据归属 / 注入防护，每关给处理位置（文件 + 行号）与验证方式。
6. **水平越权**：用户 A 访问用户 B 的资源被拒绝，测试记录完整。
7. **无字符串拼接用户输入**：SQL / 命令 / 模板全部使用参数化查询或安全 API。
8. **认证与密钥**：token 有效期和刷新规则已定；密钥只从环境变量读取，不入库、不进前端产物、不写入日志，`.env` 在 `.gitignore`。
9. **跨域 / 角色 / 限流**：跨域只允许明确来源；角色 × 接口矩阵存在，管理员接口后端单独校验；登录、注册、验证码、发送类接口有频率上限。
10. **生产错误与依赖**：对外只返回错误码和用户可读信息，不暴露路径 / SQL / 调用信息；依赖审计无已知高危漏洞，锁定文件已提交。
11. **安全审查报告**：`docs/o-安全审查报告.md` 已写入文件，整改清单全部处理，无 🔴 严重项。
12. **Git 提交**：轮次数与提交数匹配，含通过业务门之前的最后一次提交。

---

## 自动验收流程

1. 对照功能清单、测试记录、安全报告、Git 历史逐项检查。
2. 每项收集证据：文件路径 / 行号 / 命令输出。
3. 生成验收报告，每项标注 ✅ / ❌ + 证据或整改建议。
4. 全部通过 → 推进到上线门；有未通过 → 列整改清单，不推进状态。

---

## 常见遗漏项（反模式检查）

- ⚠️ 一口气写完所有业务，跳过每轮验收
- ⚠️ 改了规则不改真源文档和 API 接口清单
- ⚠️ 一个模块未验收就开下一个
- ⚠️ 只测成功路径
- ⚠️ 用 mock 代替数据库做接口测试
- ⚠️ 写接口不测重复提交，用户连点两次产生两条记录
- ⚠️ token 没有有效期和刷新规则
- ⚠️ 密钥写进代码或提交进仓库，或被打进前端构建产物
- ⚠️ 跨域配置为通配符并允许携带凭证
- ⚠️ 管理员接口只在前端隐藏入口，后端没有角色校验
- ⚠️ 登录和发送验证码接口没有频率限制
- ⚠️ 生产环境返回调用信息、SQL 或文件路径
- ⚠️ 依赖有已知高危漏洞却未处理
- ⚠️ 安全只做"要不要登录"忽略水平越权
- ⚠️ 让 AI 自己写过滤规则代替参数化查询
- ⚠️ 整改时顺手改其他代码
- ⚠️ 安全审查不给证据

## 验收结果处理

### 全部通过

1. 更新 `PROJECT_STATUS.agent.md`：`current_gate` 改为 `上线门`，`current_phase` 改为 `13`，`gate_entered_at` 改为今天，验收清单全部勾选。
2. Git 提交：`git commit -m "chore: 通过业务门"`。
3. 提示用户：进入上线门，下一步是上线前总验收。

### 有未通过项

1. 生成整改清单（未通过指标 + 原因 + 整改建议）。
2. 不推进状态，整改后重新执行本验收。
3. 直到全部通过才推进状态。
