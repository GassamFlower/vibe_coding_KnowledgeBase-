# 立项门自动验收

> 对照 `../../templates/门禁卡-立项门.md` 逐项收集证据并判定通过/不通过。

---

## 过门禁标准（10 项必须满足的指标）

1. **PRD 已写入文件**：`docs/a-立项文档.md` 按五段结构（背景目标 / 方案概述 / 具体方案 / 上线计划 / 附录）覆盖 10 项内容（立项说明 / 用户证据 / 功能边界 / Out-of-Scope / 流程路径 / 业务对象 / 技术路线 / 风险清单 / 里程碑 / 验收规则）。证据：文件路径 + 章节标题。
2. **用户证据 ≥3 条**：访谈原话 / 真实行为 / 竞品数据，每条标来源类型和证据强度；朋友夸奖、假设性回答不计入。证据：证据条目 + 来源 + 强度。
3. **Out-of-Scope 已写明**：必须有 / 后续版本 / 明确不做三组分开，每条不做的事项写原因和重新评估时间。证据：三组清单。
4. **功能清单三维度**：按角色 / 业务流程 / 模块梳理，每个功能写清给谁用 / 输入 / 输出 / 权限 / 正常流程 / 异常边界；复杂功能单独成文并留索引。
5. **阶段计划**：第一阶段是 MVP，每个阶段包含哪些功能、为什么这么排已说明，不细化到技术实现。
6. **技术选型唯一推荐**：`docs/d-选型.md` 写明前端 / 后端 / 数据库 / SDK、运行时版本、包管理器；至少 3 个被淘汰方案及理由；重新评估条件；`.env.example` 不含真值；README 能照着从零跑起来。
7. **风险清单**：需求 / 技术 / 合规 / 上线四类都有条目，每条写影响和应对策略。
8. **架构设计 7 项规则**：目录结构 / 接口响应 / 错误处理 / 日志 / 数据库连接 / 权限入口 / 框架复用边界。
9. **Agent 宪法**：≤200 行，禁止事项 ≥5 条，含验收标准、框架优先原则、成本与上下文约束；各 IDE 入口文件只写引用。
10. **Git 与忽略项**：至少 4 次提交（立项 / 选型 / 架构设计 / 宪法）；`.gitignore` 含 node_modules / dist / .env / *.log。

---

## 自动验收流程

1. 逐项检查文件存在性、内容结构、Git 历史。
2. 每项收集证据：文件路径 / 关键行号 / 命令输出。
3. 生成验收报告，每项标注 ✅ 通过 / ❌ 未通过 + 证据或整改建议。
4. 全部通过 → 推进到架构门；有未通过 → 列整改清单，不推进状态。

---

## 常见遗漏项（反模式检查）

- ⚠️ 立项文档只在对话里聊过，没有写入文件
- ⚠️ 把朋友夸奖、假设性回答当成用户证据
- ⚠️ 没有 Out-of-Scope，第一版范围无限扩大
- ⚠️ 风险清单只写技术风险，漏了需求、合规和上线风险
- ⚠️ 功能清单只按模块梳理，漏了角色和业务流程维度
- ⚠️ 技术选型让 AI 列多方案（必须唯一推荐）
- ⚠️ 选型没写运行时版本和包管理器，换台机器跑不起来
- ⚠️ 只有代码没有 README 和 `.env.example`
- ⚠️ 宪法写"建议""尽量"，或超过 200 行，或漏了成本约束
- ⚠️ IDE 入口文件复制了宪法内容（应该只写引用）
- ⚠️ 项目没建 `.gitignore`，`.env` / node_modules 进了仓库

## 验收结果处理

### 全部通过

1. 更新 `PROJECT_STATUS.agent.md`：`current_gate` 改为 `架构门`，`current_phase` 改为 `5`，`gate_entered_at` 改为今天，验收清单全部勾选。
2. Git 提交：`git commit -m "chore: 通过立项门"`。
3. 提示用户：进入架构门，下一步是实施真源文档分解。

### 有未通过项

1. 生成整改清单（未通过指标 + 原因 + 整改建议）。
2. 不推进状态，整改后重新执行本验收。
3. 直到全部通过才推进状态。
