# Skill: systematic-debugging（系统化调试）

## 何时使用

- 用户报告 bug、报错、行为异常；
- 用户说"帮我修一下""这里有问题""跑不起来"；
- 改了一个地方导致另一个地方出错。

## 解决什么问题

防止 AI 凭直觉乱猜、打补丁、改着改着把项目改乱。核心原则：**不要猜，先找根因。**

## 执行流程

1. **先复现**：让用户提供或自己构造最小复现步骤。复现不了就不能说"修好了"。
2. **收集证据**：
   - 完整错误信息（栈、日志、HTTP 状态码、响应体）；
   - 触发场景（什么操作、什么参数、什么环境）；
   - 最近一次正常的版本 / 提交；
   - 相关文件、相关接口、相关数据。
3. **提出假设**：列出至少 2-3 个可能的根因，并标注每个假设的依据。不要只列一个最省事的猜测。
4. **验证假设**：用最小代价验证每个假设（看日志、跑查询、加临时日志、看网络请求），逐个排除。
5. **定位根因**：明确说出根因是什么、在哪一行/哪一层。不能只说"可能是 XX 问题"。
6. **设计修复方案**：说明修复思路、影响范围、是否触及真源文档规则、是否需要更新 schema/migration。
7. **实施修复**：按方案改代码。改动尽量小、聚焦根因，不顺手"优化"周边代码。
8. **回归验证**：复现步骤重新跑一遍，确认 bug 消失；同时跑一遍相关功能确认没引入新问题。
9. **总结留痕**：在对话或日志里记录根因、修复方案、验证证据。必要时写进项目真源文档的"历史问题"章节。

## 止损升级机制（连续 3 轮修不好）

上面的 9 步默认一轮修好。如果同一个 bug 反复修不好，触发下面的升级机制。

**什么时候刹车**："1 轮失败" = AI 提出一个明确原因 → 针对该原因完成一次修改 → 重新走一遍原来出错的过程 → 仍然失败。**连续 3 轮失败 = 停**，不再让它试——这说明它一开始对根因的判断就是错的，继续修是在错误方向上叠加，越修越乱。

**额外刹车信号**（没到 3 轮也警惕）：
- 每轮给出的"原因"都不一样（在猜，不是定位）
- 同一处代码改了 3 次以上
- 开始波及本轮范围外的代码（慌了、打补丁）
- 话术从断言退化成"可能""大概""试试这样"
- 开始提议"重构/重写"整个模块（想绕开而不是解决）

> 刹车判断权在人，不用问 AI 要不要停——AI 倾向于一直试下去，它不知道自己错了。

**刹车动作**：说停 → Git 盘点（`git log --oneline -5` + `git diff`）→ 回退到最后稳定提交。不要在翻车现场上开新对话。

**刹车后四步走**：

1. **钉住现象**：复现步骤 / 预期 vs 实际 / 报错原文 / 环境（分支、数据、配置）/ 稳定复现还是偶发
2. **翻出前三轮**：`git log` + `git diff` 看每轮改了什么——① 告诉新对话"这些路试过且错了"；② 前三轮的改动可能是新 bug 来源；③ 它们为什么错 = 根因的线索
3. **换新对话 + 补真源**：老对话堆了 3 轮错误猜测，换新对话清场重来。必须带三样弹药：现象卡片 / 前三轮改动清单 / 真源文档。开头明说"不要沿用老对话任何结论"
4. **逼根因**：禁止"我改一下试试"。先要：直接触发点（文件+行号+代码路径）、为什么这里会出错（数据流/状态流转/边界条件）、证据（日志/调用链/能复现的测试）、修复方案+为什么修的是根因不是症状、回归风险。表述走"现象→假设→验证→结论"证据链。给不出根因就缩小范围：写最小复现脚本 / 二分定位 / 先写一个稳定触发 bug 的测试再修

**盲区提醒**：
- 偶发 bug 可能是环境 / 时序 / 并发 / 缓存问题，排查路径不同，别硬套根因流程
- 排除三类"根因假象"：修表象（把报错藏起来）、修错层（前端拦住了但后端还漏）、修复本身引入新 bug
- 换对话不行就换方案（技术栈 / 模型能力天花板，别无限换对话）
- 时间止损：没到 3 轮但修超半天，也值得停下重估方向
- 修好后把根因和"前三轮为什么错"写进真源文档历史问题章节，反哺知识库

## 输出

- 一份调试报告：根因 / 证据 / 修复方案 / 影响范围 / 回归验证结果。
- 修复后的代码改动。

## 约束

- ❌ 不在没复现的情况下"凭感觉"改代码；
- ❌ 不只列一个假设就动手；
- ❌ 不打补丁式修复（掩盖症状而不是修根因）；
- ❌ 不顺手重构无关代码；
- ❌ 不在没回归验证的情况下宣布"修好了"；
- ❌ 同一个 bug 连续 3 轮失败还继续试（必须停，换对话重来）；
- ❌ 换新对话后沿用旧对话的错误结论。
