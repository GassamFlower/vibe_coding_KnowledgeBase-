# Skill: ui-design-system（界面设计规范）

## 何时使用

- 进入架构门，准备搭前端骨架；
- 用户说“帮我设计界面”“让页面好看一点”“统一一下风格”；
- AI 生成的页面颜色、字号、间距各不相同；
- 准备接入组件库，或者已有组件库但使用方式混乱；
- 需要检查响应式、加载状态、空状态、错误状态和可访问性。

## 解决什么问题

防止 AI 每做一个页面就新增一套样式。把“好看”变成可检查的设计规范，让页面之间保持一致，让前端骨架能够被验收。

## 执行流程

### 第 1 步：先定一句风格方向

用一句话写清界面气质，例如“克制的工具型界面，浅色底，信息密度中等，重点操作使用单一强调色”。

规则：

- 只选一个方向，不同页面不允许各自发挥；
- 方向词要能指导取舍，例如“克制”“紧凑”“留白充足”“高对比”；
- 不堆形容词，不写“高端大气上档次”这类无法执行的描述。

### 第 2 步：定义设计 token

至少定义以下内容，并写入项目内的设计规范文件：

| 类别 | 内容 |
|---|---|
| 颜色 | 背景、表面、主文字、次要文字、边框、主色、危险、成功、警告 |
| 字体 | 字体族、字号阶梯、行高、字重 |
| 间距 | 4 或 8 的倍数阶梯 |
| 圆角 | 小、中、大、全圆 |
| 阴影 | 卡片、浮层、弹窗 |
| 断点 | 手机、平板、桌面 |
| 层级 | 下拉、吸顶、弹窗、提示 |

规则：

- 页面和组件只能使用 token，不直接写十六进制颜色和随手取的字号；
- token 名称使用语义名称，例如 `color-text-muted`，不使用 `gray-3` 这类无法表达用途的名称；
- 设计 token 一旦确定，新增颜色或字号必须先改规范，再改页面。

### 第 3 步：选择一个组件库

- 只选一个主组件库，不混用多套；
- 基础组件统一从组件库引入，业务组件在基础组件上封装；
- 页面里不允许大量覆盖组件库样式；
- 组件变体写进设计规范，例如按钮的主次、危险、禁用、加载状态。

### 第 4 步：定义布局与响应式

- 采用移动优先，先保证窄屏可用，再扩展宽屏；
- 写清内容最大宽度、栅格列数、页面边距；
- 触控目标不小于 44 像素；
- 不允许出现横向滚动条；
- 导航、表格、表单在小屏下要有明确的折叠或滚动策略。

### 第 5 步：补齐页面状态

每个页面至少检查以下状态：

- 加载中：骨架屏或明确的加载提示；
- 空状态：说明为什么为空，下一步能做什么；
- 错误状态：错误原因、重试入口、不会只显示“出错了”；
- 禁用状态：为什么禁用，如何恢复；
- 交互状态：悬停、聚焦、按下、选中；
- 成功状态：操作完成后用户能看到结果。

### 第 6 步：可访问性底线

- 正文文字与背景对比度达到 4.5:1；
- 键盘可以到达所有可操作元素，聚焦轮廓可见；
- 使用语义标签，按钮就是按钮，链接就是链接；
- 图片有替代文本，装饰图片标记为空；
- 表单有标签，错误提示和字段关联；
- 尊重“减少动态效果”的系统设置。

### 第 7 步：让 AI 遵守规范

在项目宪法或入口文件中写明：

- 新增页面前先读取设计规范文件；
- 新增颜色、字号、间距必须先使用已有 token；
- 新增组件先检查是否已有同类组件；
- 修改样式后必须运行浏览器验证，检查桌面和手机宽度；
- 不允许一次修改多个页面的风格。

## 输出

- 设计规范文件（风格方向、token、组件清单、页面状态要求）；
- 设计 token 文件或主题配置；
- 组件清单（已有、待封装、禁止重复实现）；
- 页面验收清单（响应式、状态、可访问性）。

## 约束

- ❌ 不在页面里直接写十六进制颜色和随手取的字号；
- ❌ 不混用多套组件库；
- ❌ 不允许每个页面一套风格；
- ❌ 不只做悬停效果，忽略键盘聚焦；
- ❌ 不允许只有加载完成后的正常状态，缺少空状态和错误状态；
- ❌ 不把“好看”当成验收标准，必须写成规范条目。
