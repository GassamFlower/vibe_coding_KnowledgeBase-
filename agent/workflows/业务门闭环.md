# 业务门完整闭环

> 从"通过架构门"到"通过业务门"的完整执行流程。
> 输入：架构门已通过（current_gate=业务门，current_phase=11）
> 输出：通过业务门验收，进入上线门
> 适用状态：开发中（架构搭完，进入业务模块开发）

---

## 前置条件

- 项目已通过架构门：`PROJECT_STATUS.agent.md` 中 `current_gate=业务门`、`current_phase=11`
- 已有：宪法 / 真源文档（实施真源文档 + 后端/前端架构实施真源文档）/ 可运行骨架 / 联调报告 / API 接口清单
- 如果架构门未通过，先走 `../workflows/架构门闭环.md`

---

## 执行流程

### Step 0：衔接与定位

1. 读取 `PROJECT_STATUS.agent.md`，确认 `current_gate=业务门`、`current_phase=11`
2. 确认架构门产出齐全（实施真源文档 / 两份架构实施真源文档 / API 接口清单 / 骨架可运行）
3. 若不齐全，回到架构门闭环补齐，不进入业务门

---

### Step 1：业务模块开发（阶段 11，多轮循环）

**目标**：按实施真源文档逐个交付业务模块，一轮一验收

#### 每轮开始前（段 1 对话挖掘，用户主导）

智能体进入"业务模块开发"角色，先出本轮计划：

1. 接口清单（对照 `docs/i-API接口清单.md`：路径 / 方法 / 入参 / 出参 / 权限 / P0-P2）
2. 页面清单（路由 / 组件 / 状态 / P0-P2）
3. 涉及的业务对象 / 表变更（有变更先改 schema）
4. 涉及的规则变更（有变更先改真源文档和 API 接口清单）
5. 本轮划分（一个模块分 N 轮）
6. 每轮验收标准

**关键**：本轮范围限定（只做计划内的任务），一个模块未验收不开下一个。

**调用子能力**：`writing-plans`（写模块开发计划）

#### 每轮执行（段 3 执行交付，智能体主导）

- 按计划实现接口 / 页面
- 接口输入后端重新校验、权限校验到位、敏感数据哈希
- 数据变更先改 schema 再动代码
- 关键操作加日志
- 核心接口补自动化测试
- 核心流程按真实用户路径做端到端验证

#### 每轮完成前（段 4 验收固化）

智能体调用完成前验收 prompt（对应门禁卡-业务门），逐项交证据：

- 功能：核心路径走通了吗？给执行命令和输出
- 规则：有没有违反宪法 / 真源文档？
- 安全：接口输入后端重新校验了吗？权限校验在哪里？
- 数据：数据库变更先改 schema 了吗？
- 接口：返回示例覆盖成功 / 失败 / 边界了吗？
- 测试：核心接口的自动化测试跑过了吗？给运行命令和结果
- 端到端：核心用户流程实际走过了吗？给页面结果和数据库结果
- 幂等：重复提交验证过吗？不产生重复数据
- 日志：关键操作有日志吗？
- 回归：相邻功能没被破坏吧？给证据

**调用子能力**：`testing-strategy`（测试六步法）+ `verification-before-completion`（宣布完成前必走）

每项给文件 / 命令 / 输出 / 日志作为证据。未验证项标记"未验证"。不允许写"基本完成"。

测试要求：
- 每个接口覆盖：成功、必填缺失、类型错误、未登录、无权限、访问他人数据、资源不存在
- 列表接口覆盖：空列表、分页边界、非法排序字段
- 写接口覆盖：重复提交（幂等）、事务回滚、并发冲突
- 测试使用真实数据库或测试数据库，不用 mock 代替数据库
- 核心流程（注册 → 登录 → 创建 → 支付或提交 → 查看结果）端到端走一遍

#### 每轮结束后

- Git 提交：`git commit -m "feat: 完成模块 [模块名] 第 N 轮"`
- 更新模块清单（做啥 / 做了啥 / 待优化 / 可上线 / 阻塞）
- 进入下一轮，直到所有 P0 功能完成；P1/P2 写明"未做 / 延后"原因

---

### Step 2：后端安全审查（阶段 12）

**目标**：5 道关卡全过，安全审查报告写入文件

#### 段 1 对话挖掘

智能体进入"安全审查员"角色。明确告诉用户：**本轮不改代码，只审查**。

#### 段 2 整理成文 + 段 3 执行交付

按 5 道关卡逐关说明：

1. 身份认证：哪些接口需要登录，在哪里校验；token 有效期和刷新规则
2. 权限控制：哪些接口限定角色，无权限返回什么；角色 × 接口矩阵；管理员接口单独校验
3. 输入校验：关键参数在哪里后端重新校验
4. 数据归属：水平越权测试（用户 A 不能访问用户 B 的资源）
5. 注入防护：无字符串拼接用户输入（参数化查询）

每道关卡给：风险 / 处理位置（文件 + 行号）/ 处理规则 / 如何验证 / 是否通过。

密钥与访问控制逐项核对：
- 密钥只从环境变量读取，不入库、不进前端代码、不写入日志，`.env` 在 `.gitignore` 里
- 跨域只允许明确列出的来源，凭证请求有对应配置
- 登录、注册、验证码、发送类接口有频率上限
- 生产错误信息只返回错误码和用户可读信息，不暴露路径、SQL、调用信息
- 依赖审计命令无已知高危漏洞，锁定文件已提交

**调用子能力**：`backend-security-review`（防"已做安全处理"敷衍）

#### 段 4 验收固化

- 输出整改清单，按严重 / 风险 / 建议分级
- 整改清单全部处理（每项整改后重新验证）
- 生成 `docs/o-安全审查报告.md`
- Git 提交：`git commit -m "chore: 完成安全审查并写入报告"`

---

### Step 3：业务门自动验收

智能体调用 `../gate-checks/业务门.md`，执行自动验收：

1. 逐项检查 12 项必须满足的指标（P0 完成 / 每轮验收证据 / 测试六步法 / 接口自动化 + 端到端 / 安全 5 关 / 越权 / 注入 / 认证与密钥 / 跨域角色限流 / 依赖审计 / 报告 / Git）
2. 收集证据（文件路径 / 行号 / 命令输出 / git log）
3. 检查反模式（常见遗漏清单）
4. 生成验收报告

#### 如果全部通过

1. 更新 `PROJECT_STATUS.agent.md`：
   - `current_gate` 改为 `上线门`
   - `current_phase` 改为 `13`
   - `gate_entered_at` 改为今天
   - 验收清单全部勾选 ✅
2. Git 提交：`git commit -m "chore: 通过业务门"`
3. 提示用户：可以进入上线门了，下一步是上线前总验收

#### 如果有未通过项

1. 生成整改清单（每项：未通过指标 + 原因 + 整改建议）
2. 不推进状态
3. 智能体协助整改，整改后重新执行本验收
4. 直到全部通过才推进状态

## 完成判定

业务门闭环完成当：

- [ ] 所有 P0 功能完成，P1/P2 有明确说明
- [ ] 每轮都有验收证据
- [ ] 每个模块走过测试六步法
- [ ] 核心接口有自动化测试，核心流程有端到端验证
- [ ] 安全审查 5 关全过、水平越权通过、无字符串拼接用户输入
- [ ] 认证与密钥管理、跨域白名单、角色权限矩阵、限流四项已核对
- [ ] 依赖审计无已知高危漏洞
- [ ] `docs/o-安全审查报告.md` 已写入文件
- [ ] PROJECT_STATUS 已更新（current_gate = 上线门）
- [ ] 已 Git 提交"通过业务门"
- [ ] 智能体已提示用户进入上线门

## 反模式（执行过程中避免）

- ❌ 一口气写完所有业务（必须分轮）
- ❌ 跳过每轮验收
- ❌ 改了规则不改真源文档和 API 接口清单
- ❌ 一个模块未验收就开下一个
- ❌ 安全只做"要不要登录"忽略水平越权
- ❌ 让 AI 自己写过滤规则代替参数化查询
- ❌ 整改时顺手改其他代码
- ❌ 安全审查不给证据
- ❌ 只测成功路径（参数错误、未登录、无权限、访问他人数据都没测）
- ❌ 用 mock 代替数据库做接口测试
- ❌ 写接口不测重复提交
- ❌ token 没有有效期和刷新规则
- ❌ 密钥写进代码或提交进仓库
- ❌ 跨域配置为通配符并允许携带凭证
- ❌ 管理员接口只在前端隐藏入口，后端没有角色校验
- ❌ 登录和发送验证码接口没有频率限制
- ❌ 生产环境返回调用信息、SQL 或文件路径
- ❌ 依赖有已知高危漏洞却未处理
- ❌ 验收用"基本完成"等模糊词
- ❌ 没有证据就标记"通过"
- ❌ 没过业务门就进入上线门
