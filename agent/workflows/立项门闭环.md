# 立项门完整闭环

> 从"纯想法"到"通过立项门"的完整执行流程。
> 输入：项目想法
> 输出：通过立项门验收，进入架构门
> 适用状态：状态 0（纯想法，没代码没文档）

---

## 前置条件

- 项目处于状态 0（纯想法）：没代码没文档
- 如果有代码，先走 `../state-machine.md` 的状态判断决策树

---

## 执行流程

### Step 0：状态判断 + 初始化

1. 确认项目处于状态 0（没代码没文档）
2. 创建项目文件夹（英文 + 中划线，如 `task-manager`）
3. 复制 `../templates/PROJECT_STATUS.agent.md` 到项目根目录，重命名为 `PROJECT_STATUS.md`
4. 初始化 Git：`git init`
5. 创建 `.gitignore`，至少包含 `node_modules` / `dist` / `.env` / `*.log`
6. 创建 `README.md` 骨架（项目名 / 一句话说明 / 后续补安装启动命令）
7. 更新 PROJECT_STATUS：
   - `project_name`：项目名
   - `start_date`：今天
   - `current_state`：0
   - `current_phase`：1
   - `current_gate`：立项门
   - `gate_entered_at`：今天

---

### Step 1：立项（阶段 1）

**目标**：把想法变成 PRD + 功能清单 + 阶段计划

#### 段 1 对话挖掘（用户主导）

智能体进入"产品合伙人"角色，明确告诉用户：**当前只做产品讨论，不写代码**。

智能体围绕以下问题深挖：
- 项目类型、目标用户、核心问题
- 用户证据：至少 3 条真实证据（访谈原话 / 真实行为 / 竞品数据），标注来源类型和证据强度
- MVP 边界（第一版做什么、不做什么）
- Out-of-Scope：明确不做的事项，每条写原因和重新评估时间
- 长期规划
- 风险：需求 / 技术 / 合规 / 上线四类
- 主动指出盲区：权限、数据结构、状态字段、后期扩展、合规风险

朋友的夸奖、假设性回答、没有具体行为的描述不算用户证据，单独标出，不计入 3 条。

智能体给**唯一推荐**，不列多方案。讨论清楚后，智能体说"现在可以写立项文档了"，等用户确认。

**调用子能力**：`brainstorming`

#### 段 2 整理成文（智能体起草 + 用户确认）

智能体生成 3 份文档（写入 `docs/`，按字母前缀命名，见操作手册 0.3）：

1. **`docs/a-立项文档.md`**（PRD 五段：背景目标 / 方案概述 / 具体方案 / 上线计划 / 附录），覆盖 10 项内容：
   1. 项目立项说明：是什么 / 面向谁 / 解决什么问题 / 为什么值得做 / 第一版核心目标
   2. 用户证据：至少 3 条真实证据 + 来源类型 + 证据强度
   3. 项目核心功能和边界：第一版做什么、不做什么
   4. Out-of-Scope：明确不做的事项 + 原因 + 重新评估时间
   5. 产品流程和用户路径
   6. 数据和业务对象
   7. 技术路线初步判断
   8. 风险清单：需求 / 技术 / 合规 / 上线
   9. 后期规划和里程碑
   10. 验收规则：可检查的标准

2. **`docs/b-功能清单.md`**（三维度组织）：
   - 按角色 / 按业务流程 / 按模块
   - 每个功能：给谁用 / 输入 / 输出 / 权限 / 正常流程 / 异常边界
   - 复杂功能单独写文档 + 留索引（订单流转 / 支付退款 / 优惠叠加 / 权限系统）

3. **`docs/c-阶段计划.md`**：
   - 第一阶段必须是 MVP（能跑通核心流程的最小可用版本）
   - 每个阶段包含哪些功能、为什么这么排
   - 只给大阶段划分，不细化到技术实现

**调用子能力**：`project-breakdown` + `writing-plans`

用户 review，看不懂的地方让智能体用大白话讲。

#### 段 4 验收固化

- 更新 PROJECT_STATUS：勾选立项阶段完成
- Git 提交：`git commit -m "chore: 完成项目立项"`

---

### Step 2：技术选型（阶段 2）

**目标**：确定唯一推荐技术方案

#### 段 1 对话挖掘

智能体进入"架构顾问"角色。基于立项文档，给**唯一推荐技术方案**。

必须说明：
- 前端框架 + UI 组件库
- 后端语言 + 框架
- 数据库
- 运行时版本 + 包管理器 + 数据库版本（换台机器能照着重装）
- 为什么选它们（结合项目情况）
- 为什么不选其他常见方案（至少 3 个被淘汰方案）
- 什么情况下需要重新评估

画边界：必须遵守当前框架官方规范，优先选成熟框架和 SDK。

#### 段 2 整理成文

智能体生成 `docs/d-选型.md`，包含：
- 产品形态
- 前端 / 后端 / 数据库 / SDK 列表
- 运行时版本 / 包管理器 / 数据库版本
- 选的理由
- 不选的理由
- 重新评估条件

同时补齐可复现环境：
- `.env.example`：写清每个变量填什么，不放真实值
- `README.md`：安装 / 启动 / 构建命令，照着能从头跑起来

#### 段 4 验收固化

- Git 提交：`git commit -m "chore: 确定项目技术方案"`

---

### Step 3：架构设计文档（阶段 3）

**目标**：确定目录结构、接口规则、错误处理等架构规则

#### 段 1 对话挖掘

智能体输出架构设计文档**大纲**，用户确认大纲后再写完整版。

#### 段 2 整理成文

智能体生成架构设计文档，包含 7 项核心规则：
1. 目录结构规则（每个目录职责 / 放什么 / 不放什么）
2. 接口响应规则（统一格式 + 错误码表 + 分页规则）
3. 错误处理规则（异常捕获 / 日志记录 / 返回格式）
4. 日志规则（级别 / 格式 / 关键操作清单）
5. 数据库连接规则（连接池 / 事务边界 / ORM 使用规范）
6. 权限入口（认证中间件 / 角色校验 / 数据归属校验位置）
7. 框架复用边界（必须用框架 / 可封装 / 禁止自造）

写入 `docs/e-架构设计文档.md`。

#### 段 4 验收固化

- Git 提交：`git commit -m "chore: 完成架构设计文档"`

---

### Step 4：Agent 宪法（阶段 4）

**目标**：创建 Agent 宪法基础版，给 AI 立规矩

#### 段 1 对话挖掘

智能体进入"项目架构顾问"角色。基于立项 + 选型 + 架构设计，起草宪法大纲。

三条写作原则：
- **短**：不超过 200 行
- **明确**：每条都是必须遵守的规则，能直接判断对错
- **清楚**：不写"建议""尽量"等模糊说法

只写长期原则，不写具体技术细节（细节放架构设计文档或真源文档）。

#### 段 2 整理成文

智能体生成 `AGENT_CONSTITUTION.md`，包含：
- 安全诚信条款
- 诚实边界条款
- 执行铁律
- 代码生成器承诺
- 项目专属条款（≥ 5 条，基于立项 + 选型 + 架构设计的真实情况）
- 禁止事项（≥ 5 条）
- 验收标准
- 框架优先原则
- 成本与上下文约束（忽略目录 / 模型分层 / 会话熔断）

创建各 IDE 入口文件（**只写引用，不复制内容**）：
- Codex：`AGENTS.md`
- Cursor：`.cursor/rules/project.md`
- Claude Code：`CLAUDE.md`
- Trae：`.trae/rules/project.md`

入口文件内容示例：
```markdown
## 项目约束
本项目 Agent 必须遵守 AGENT_CONSTITUTION.md 中的所有规则。
请阅读 AGENT_CONSTITUTION.md 了解详细约束。
```

#### 段 4 验收固化

- Git 提交：`git commit -m "chore: 创建项目 Agent 宪法（基础版）"`

---

### Step 5：立项门自动验收

智能体调用 `../gate-checks/立项门.md`，执行自动验收：

1. 逐项检查 10 项必须满足的指标
2. 收集证据（文件路径 / 行号 / Git log）
3. 检查反模式（常见遗漏清单）
4. 生成验收报告

#### 如果全部通过

1. 更新 PROJECT_STATUS：
   - `current_gate` 改为 `架构门`
   - `current_phase` 改为 `5`
   - `gate_entered_at` 改为今天
   - 验收清单全部勾选 ✅
2. Git 提交：`git commit -m "chore: 通过立项门"`
3. 提示用户：可以进入架构门了，下一步是实施真源文档分解

#### 如果有未通过项

1. 生成整改清单（每项：未通过指标 + 原因 + 整改建议）
2. 不推进状态
3. 智能体协助整改，整改后重新执行本验收
4. 直到全部通过才推进状态

---

## 完成判定

立项门闭环完成当：

- [ ] 10 项必须满足的指标全部通过
- [ ] 反模式检查无遗漏
- [ ] PROJECT_STATUS 已更新（current_gate = 架构门）
- [ ] 已 Git 提交"通过立项门"
- [ ] 智能体已提示用户进入架构门

---

## 反模式（执行过程中避免）

- ❌ 跳过对话挖掘直接让智能体写文档
- ❌ 把朋友夸奖、假设性回答当成用户证据
- ❌ 只有"用户说想要"，没有真实行为、使用频率和代价
- ❌ 没有 Out-of-Scope，第一版范围无限扩大
- ❌ 风险清单只写技术风险，漏了需求、合规和上线风险
- ❌ 一口气做完 4 个阶段不验收
- ❌ 选型让智能体列多方案（必须唯一推荐）
- ❌ 选型没写运行时版本和包管理器
- ❌ 只有代码没有 README 和 `.env.example`
- ❌ 宪法写"建议""尽量"等模糊词
- ❌ 宪法超过 200 行
- ❌ 宪法漏了成本与上下文约束
- ❌ IDE 入口文件复制宪法内容
- ❌ 项目没建 `.gitignore`，`.env` / node_modules 进了仓库
- ❌ 没过立项门就进入架构门
- ❌ 验收用"基本完成"等模糊词
- ❌ 没有证据就标记"通过"
