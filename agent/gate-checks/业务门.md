# 业务门自动验收

> 基于 `../../templates/门禁卡-业务门.md` 转化的可执行评估项。
> 每项：检查什么 → 怎么检查 → 通过标准 → 证据要求。
> 智能体调用本文件，逐项收集证据并判定通过/不通过。

---

## 过门禁标准（12 项必须满足的指标）

### 指标 1：所有 P0 功能已开发完成

- **检查什么**：功能清单里的 P0 功能是否全部交付
- **怎么检查**：对照 `docs/a-立项文档.md` 和 `docs/b-功能清单.md`，逐项核对完成状态
- **通过标准**：P0 全部完成；P1/P2 有明确的"未做/延后"说明（不能是"基本完成"）
- **证据要求**：功能清单核对表 + 每项的完成状态

### 指标 2：每轮开发都有验收证据

- **检查什么**：业务模块是否按"一轮一验收"推进，而非一口气写完
- **怎么检查**：检查每轮的验收记录（文件 / 命令输出 / 截图）
- **通过标准**：每轮都有功能走通证据（执行命令 + 输出）；没有"本轮范围限定"之外的任务混入
- **证据要求**：每轮验收记录路径 + 关键输出

### 指标 3：每个模块走过测试六步法

- **检查什么**：模块完成前是否走 `testing-strategy` 六步法
- **怎么检查**：核对模块的测试记录（六步法各步的证据）
- **通过标准**：每个模块的测试记录完整（含"假测试/过度测试"自查）
- **证据要求**：测试记录 + 运行输出

### 指标 4：核心接口有自动化测试，核心流程有 E2E 验证

- **检查什么**：自动化测试是否覆盖核心接口和核心用户流程
- **怎么检查**：读取测试文件，实际运行测试命令和 E2E 流程
- **通过标准**：
  - 核心接口自动化测试覆盖成功、参数错误、未登录、无权限、访问他人数据、资源不存在
  - 列表接口覆盖空列表、分页边界、非法排序字段
  - 写接口覆盖重复提交、事务回滚、并发冲突
  - 核心用户流程有 E2E 验证，每步有页面结果和数据库状态
  - 测试使用真实数据库或测试数据库，不用 mock 代替数据库
- **证据要求**：测试文件路径 + 运行命令 + 完整输出 + E2E 步骤记录

### 指标 5：安全审查 5 道关卡全过

- **检查什么**：身份认证 / 权限控制 / 输入校验 / 数据归属 / 注入防护
- **怎么检查**：读取 `docs/o-安全审查报告.md`，逐关核对
- **通过标准**：5 关每关都给"风险 / 处理位置（文件+行号）/ 处理规则 / 如何验证 / 是否通过"
- **证据要求**：安全审查报告路径 + 5 关结论

### 指标 6：水平越权测试通过

- **检查什么**：用户 A 不能访问用户 B 的资源
- **怎么检查**：执行水平越权测试用例（两个不同用户身份访问同一资源）
- **通过标准**：越权访问被拒绝（返回无权限/未授权），测试记录完整
- **证据要求**：越权测试命令 + 输出

### 指标 7：无字符串拼接用户输入

- **检查什么**：SQL / 命令 / 模板是否拼接用户输入
- **怎么检查**：搜索字符串拼接模式（f-string 拼 SQL、`os.system` 拼命令等）
- **通过标准**：全部使用参数化查询 / 安全 API；无拼接用户输入
- **证据要求**：搜索命令 + 结果（无命中或已整改）

### 指标 8：认证与密钥管理检查通过

- **检查什么**：token 生命周期和密钥存储是否安全
- **怎么检查**：读取认证代码和配置，检查 `.gitignore`
- **通过标准**：
  - token 有效期、刷新规则、退出后立即失效已确认
  - 密钥只从环境变量读取
  - 密钥未入库、未进前端代码、未写入日志
  - `.env` 已加入 `.gitignore`
  - 密码规则齐全（长度 + 字符组合 + 弱密码拦截 + 哈希 + 失败限制）
- **证据要求**：配置路径 + 代码位置 + `.gitignore` 内容

### 指标 9：跨域白名单、角色权限、限流三项已配置

- **检查什么**：CORS、角色 × 接口矩阵、敏感接口限流
- **怎么检查**：读取配置和权限矩阵，实际请求验证
- **通过标准**：
  - 跨域只允许明确列出的来源，凭证请求有对应配置，不使用通配符
  - 角色 × 接口矩阵存在，管理员接口有单独校验
  - 登录、注册、验证码、发送类接口有频率上限
  - 生产错误信息不暴露路径、SQL、调用信息
- **证据要求**：配置文件路径 + 权限矩阵 + 限流测试输出

### 指标 10：依赖审计无已知高危漏洞

- **检查什么**：锁定文件是否提交，依赖是否有已知高危漏洞
- **怎么检查**：执行依赖审计命令（npm audit / pip-audit / go vuln check 等）
- **通过标准**：锁定文件已提交；审计命令无已知高危漏洞
- **证据要求**：审计命令 + 完整输出

### 指标 11：安全审查报告已写入文件

- **检查什么**：`docs/o-安全审查报告.md` 是否存在
- **怎么检查**：读取文件，检查 5 关结论 + 认证密钥 + 跨域 / 角色权限 / 限流 + 生产错误 + 依赖审计 + 整改清单
- **通过标准**：报告已写入文件、整改清单全部处理、无 🔴 严重项残留
- **证据要求**：文件路径 + 整改清单处理状态

### 指标 12：已 Git 提交

- **检查什么**：Git 提交历史（每个模块一轮一提交）
- **怎么检查**：`git log --oneline`
- **通过标准**：至少与业务模块轮次数相当的提交数，含"通过业务门"之前的最后提交
- **证据要求**：`git log` 输出

## 自动验收流程

```
1. 智能体读取本文件的 12 项必须满足的指标
2. 逐项检查（文件存在性 + 内容检查 + Git 历史）
3. 每项收集证据：
   - 文件路径
   - 关键内容行号
   - 命令输出（如 git log / 越权测试输出 / 测试运行输出）
4. 生成验收报告：

   验收报告：业务门
   ================
   指标 1 P0 功能：✅ 通过
     证据：docs/b-功能清单.md，P0 全部勾选完成
   指标 2 每轮验收：✅ 通过
     证据：docs/验收记录/模块A.md，第 3-20 行含命令输出
   指标 4 自动化测试：✅ 通过
     证据：tests/api/order.test.ts，npm test 输出 24 passed
   ...
   指标 12 Git 提交：❌ 未通过
     原因：最后几个模块没提交
     整改建议：git commit -m "feat: 完成模块X并验收"

5. 全部通过 → 推进状态到上线门
6. 有未通过 → 列出整改清单，不推进状态
```

## 常见遗漏项（反模式检查）

智能体验收时，额外检查以下反模式：

- ⚠️ 一口气写完所有业务（必须分轮，一轮一验收）
- ⚠️ 跳过每轮验收直接开下一个模块
- ⚠️ 改了规则不改真源文档
- ⚠️ 一个模块未验收就开下一个
- ⚠️ 只测成功路径（参数错误、未登录、无权限、访问他人数据都没测）
- ⚠️ 用 mock 代替数据库做接口测试（测过了，上线就报错）
- ⚠️ 写接口不测重复提交，用户连点两次就产生两条记录
- ⚠️ 安全只做"要不要登录"忽略水平越权
- ⚠️ 让 AI 自己写过滤规则代替参数化查询
- ⚠️ token 没有有效期和刷新规则，退出登录后旧 token 仍可用
- ⚠️ 密钥写进代码或提交进仓库，或被打进前端构建产物
- ⚠️ 跨域配置为通配符并允许携带凭证
- ⚠️ 管理员接口只在前端隐藏入口，后端没有角色校验
- ⚠️ 登录和发送验证码接口没有频率限制
- ⚠️ 生产环境返回调用信息、SQL 或文件路径
- ⚠️ 依赖有已知高危漏洞却未处理
- ⚠️ 整改时顺手改其他代码
- ⚠️ 安全审查不给证据，只说"已做安全处理"
- ⚠️ 用"基本完成""应该没问题"等模糊词
- ⚠️ 没有证据就标记"通过"
- ⚠️ 纯前端 / 小程序项目跳过安全审查（应改走 frontend-security-review）
- ⚠️ 没过业务门就进入上线门
