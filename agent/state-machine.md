# 项目状态机

> Vibe_Coding 工程化智能体的状态机定义。
> 5 种项目状态 × 14 个开发阶段 × 4 道门禁。
> 智能体启动时读取本文件，确定项目当前状态和下一步动作。

---

## 5 种项目状态

| 状态编号 | 状态名 | 特征 | 入口流程 |
|---|---|---|---|
| 0 | 纯想法 | 没代码没文档 | 立项门完整流程 |
| 1 | 烂尾 | 有代码跑不起来 | 烂尾抢救流程 |
| 2 | 半成品 | 能跑但残缺 | 半成品补全流程 |
| 3 | 黑盒 | 能跑但没文档 | 黑盒考古流程 |
| 4 | 健康 | 能跑 + 有文档 | 健康项目迭代 |

> **判断窍门**：90% 的"已完成项目"实际是状态 3（黑盒），不是状态 4。先按状态 3 走考古流程。

### 状态判断决策树

```
有代码吗？
├─ 没有 → 状态 0（走立项门完整流程）
└─ 有 → 能跑起来吗？
    ├─ 跑不起来 → 状态 1（烂尾抢救）
    ├─ 能跑但残缺 → 状态 2（半成品补全）
    └─ 能跑且基本完整 → 有真源文档吗？
        ├─ 没有 → 状态 3（黑盒考古）
        └─ 有 → 代码和文档对得上吗？
            ├─ 对不上 → 状态 3
            └─ 对得上 → 状态 4（健康迭代）
```

## 14 个开发阶段

| 阶段 | 名称 | 所属门禁 | 输入 | 输出 |
|---|---|---|---|---|
| 1 | 项目立项 | 立项门 | 想法 | 立项文档 + 功能清单 + 阶段计划 |
| 2 | 技术选型 | 立项门 | 立项文档 | 选型文档 |
| 3 | 架构设计文档 | 立项门 | 立项 + 选型 | 架构设计文档 |
| 4 | Agent 宪法 | 立项门 | 前 3 步 | 宪法文件 |
| 5 | 实施真源文档拆解 | 架构门 | 宪法 | 实施真源文档 |
| 6 | 前端骨架 | 架构门 | 架构设计 | 前端骨架 + 实施文档 |
| 7 | 数据库设计 | 架构门 | 前端页面 | schema.sql |
| 8 | 后端骨架 | 架构门 | 数据库设计 | 后端骨架 + 实施文档 |
| 9 | 后端联调 | 架构门 | 前后端骨架 | 联调报告 |
| 10 | 架构验收 | 架构门 | 所有骨架 | 验收报告 + 真源文档 |
| 11 | 业务模块开发 | 业务门 | 真源文档 | 可运行模块 |
| 12 | 后端安全审查 | 业务门 | 业务模块 | 安全审查报告 |
| 13 | 上线前总验收 | 上线门 | 所有产出 | 验收报告 |
| 14 | 上线 + 反哺 | 上线门 | 验收通过 | 上线 + 复盘 + Skill 更新 |

---

## 4 道门禁

| 门禁 | 包含阶段 | 过门禁标准 |
|---|---|---|
| 立项门 | 1-4 | 方向定死、技术栈定、架构设计有、AI 有规矩 |
| 架构门 | 5-10 | 真源文档有、四条线跑通、联调通、真源文档有 |
| 业务门 | 11-12 | 功能做完、安全过了 |
| 上线门 | 13-14 | 验收过、Skill 反哺了 |

## 状态流转规则

### 状态 0（纯想法）→ 立项门闭环

```
状态 0
  ↓ 启动立项门闭环（workflows/立项门闭环.md）
阶段1 立项 → 阶段2 选型 → 阶段3 架构设计 → 阶段4 宪法
  ↓ 立项门检查通过（gate-checks/立项门.md）
状态 0 → 进入架构门（状态变为"开发中"）
```

- **入口动作**：创建项目文件夹，初始化 PROJECT_STATUS.agent.md，git init
- **出口动作**：立项门验收通过，更新 PROJECT_STATUS（当前门禁 = 架构门）

### 架构门闭环（阶段 5-10）

> 立项门通过后自动进入。覆盖架构搭建 + 架构验收，直到通过架构门。

```
状态 0（已通过立项门）
  ↓ 进入架构门闭环（workflows/架构门闭环.md）
阶段5 实施真源文档拆解 → 阶段6 前端骨架 → 阶段7 数据库设计
  → 阶段8 后端骨架 → 阶段9 后端联调 → 阶段10 架构验收
  ↓ 架构门检查通过（gate-checks/架构门.md）
状态推进到业务门（current_gate=业务门, current_phase=11）
```

- **入口动作**：确认立项门产出齐全（立项 / 选型 / 架构设计 / 宪法）
- **出口动作**：架构门验收通过，更新 PROJECT_STATUS（当前_gate = 业务门，current_phase = 11），生成《后端架构实施真源文档》《前端架构实施真源文档》，宪法加引用条款

### 业务门闭环（阶段 11-12）

> 架构门通过后自动进入。覆盖业务模块开发 + 安全审查，直到通过业务门。

```
状态 0（已通过架构门）
  ↓ 进入业务门闭环（workflows/业务门闭环.md）
阶段11 业务模块开发（多轮，一轮一验收）→ 阶段12 后端安全审查
  ↓ 业务门检查通过（gate-checks/业务门.md）
状态推进到上线门（current_gate=上线门, current_phase=13）
```

- **入口动作**：确认架构门产出齐全（真源文档 / 骨架 / 联调报告）
- **出口动作**：业务门验收通过，更新 PROJECT_STATUS（当前_gate = 上线门，current_phase = 13），生成《安全审查报告》，Git 提交"通过业务门"

### 上线门闭环（阶段 13-14）

> 业务门通过后自动进入。覆盖上线前总验收 + 上线 + Skill 反哺，直到项目收官。

```
状态 0（已通过业务门）
  ↓ 进入上线门闭环（workflows/上线门闭环.md）
阶段13 上线前总验收（5 维度审查）→ 阶段14 上线 + Skill 反哺
  ↓ 上线门检查通过（gate-checks/上线门.md）
项目收官（current_gate=无(已上线), current_phase=14, current_state=4）
```

- **入口动作**：确认业务门产出齐全（P0 功能 / 安全审查报告）
- **出口动作**：上线门验收通过，更新 PROJECT_STATUS（已上线 / 状态 4），生成《上线前验收报告》《项目复盘》，反哺至少 1 条经验到 skills/，Git 提交"通过上线门"

### 状态 1（烂尾）→ 烂尾抢救

```
状态 1
  ↓ 烂尾抢救流程
停 → Git 盘点（git log --oneline -20）→ 找到最后能跑的提交 → 回退
  ↓ 回退到稳定版本
状态 1 → 状态 3（转入黑盒考古）
```

- **入口动作**：立即停止继续补，执行 Git 盘点
- **出口动作**：回退到稳定版本，转入状态 3

### 状态 2（半成品）→ 半成品补全

```
状态 2
  ↓ 半成品补全流程
反推已有真源 → 梳理已完成 vs 待完成 → 立宪法 → 补未完成部分
  ↓ 规则固化
状态 2 → 状态 4（健康迭代）或 状态 3（需进一步考古）
```

- **入口动作**：让智能体读代码反推已有规则
- **出口动作**：规则固化后，进入健康迭代或考古流程

### 状态 3（黑盒）→ 黑盒考古

```
状态 3
  ↓ 黑盒考古（三阶段）
阶段1 反推固化（不整改）→ 阶段2 Skill 校验（不整改）→ 阶段3 分批整改 + 反哺
  ↓ 考古完成
状态 3 → 状态 4（健康迭代）
```

- **入口动作**：让智能体读代码，反推三份真源文档（后端/前端/数据库）
- **出口动作**：考古完成，进入健康迭代

### 状态 4（健康）→ 健康迭代

```
状态 4
  ↓ 健康迭代
每个新需求：拆计划 → 每轮验收 → 规则变更同步 → 盲点反哺
  ↓ 项目结束
状态 4 → 上线门 → 反哺知识库
```

- **入口动作**：直接进入迭代
- **出口动作**：项目结束，走上线门 + 反哺

## 状态机读取方式

智能体启动时：

1. 读取项目的 `PROJECT_STATUS.agent.md`
2. 解析 frontmatter 中的 `current_state`、`current_phase`、`current_gate`
3. 根据状态流转规则，确定下一步动作
4. 调用对应的 workflow 执行

如果 `PROJECT_STATUS.agent.md` 不存在：
1. 走状态判断决策树，判断项目状态
2. 创建 `PROJECT_STATUS.agent.md`，填入判断结果
3. 进入对应状态的入口流程

## 状态推进的硬约束

1. **没有通过门禁检查，不允许推进状态** — 必须调用 `gate-checks/` 验收通过
2. **没有证据，不允许标记"通过"** — 每项验收必须有文件路径/命令输出/截图
3. **未验证项必须标记"未验证"** — 不允许写"基本完成"
4. **状态推进必须更新 PROJECT_STATUS** — 状态文件是单一真相来源
5. **状态推进必须 Git 提交** — `git commit -m "chore: 通过 XX 门禁"`
