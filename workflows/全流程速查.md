# Vibe Coding 全流程速查

> 14 个阶段合并为 1 个速查手册。每个阶段保留：触发条件、核心步骤、完成判定、反模式。
> 详细操作见 [AI协作全流程操作手册](../docs/AI协作全流程操作手册.md)。
>
> 📄 **项目文档命名**：各阶段生成的文档统一放项目 `docs/`，按字母前缀排序（`a-立项文档` → `b-功能清单` → `c-阶段计划` → `d-选型` → `e-架构设计文档` → `f-实施真源文档` → `g-前端架构实施文档` → `h-数据库设计文档` → `i-后端架构实施文档` → `i-API接口清单` → `j-联调报告` → `k/l-前后端真源文档` → `m-架构验收报告` → `n-模块清单` → `o-安全审查报告` → `p-上线前验收报告` → `p-上线检查清单` → `q-项目复盘报告` → `r-上线后30天迭代计划`）。文件名排序 = 流程顺序。宪法 `AGENT_CONSTITUTION.md` 放项目根目录不参与前缀。完整对照表见操作手册 0.3。

## 阶段顺序总览

```
1. 立项规划（含功能清单 + 阶段计划）
2. 技术选型
3. 架构设计文档（代码怎么组织、目录怎么放）
4. Agent 宪法（基于前 3 步的真实情况，一点点攒出来）
5. 实施真源文档分解（大阶段 → 子阶段 → 步骤）
6. 前端骨架搭建
7. 数据库设计
8. 后端骨架搭建
9. 后端联调
10. 架构验收（后端 + 前端）
11. 业务模块开发（一个模块一个模块写接口，边写边接前端，做完一个模块就验收 + 提交 git）
12. 后端安全审查
13. 上线前总验收
14. 上线 + Skill 反哺
```

**为什么是这个顺序**：架构设计文档在选型后（技术方案没确定，目录无从谈起）；宪法在架构设计文档后（好宪法必须结合项目真实情况）；实施真源文档在宪法后（长期原则先于阶段细则）；前端骨架在数据库前（骨架只搭壳不接数据）；数据库在后端骨架前（骨架要连库验证）；联调在骨架后（跑通才能接）；验收在联调后（看实际实现）；业务开发在验收后（地基稳才盖楼）。

## 01 项目立项

**触发条件**：准备开始新项目 / 旧项目重来
**输入**：脑子里的产品方向 + 参考产品（可选）
**输出**：立项文档（PRD）+ 功能清单 + 阶段计划

### 核心步骤
1. 创建空项目文件夹（英文 + 中划线/下划线）
2. 进入"产品合伙人"模式（明确告诉 AI：当前阶段只做产品讨论，不要写代码）
3. **需求验证**（写任何文档前先做）：收集至少 3 条真实用户证据（访谈原话 / 真实行为 / 数据），每条标明来源类型和证据强度；朋友夸奖、假设性回答、没有具体行为的描述不算证据，单独列出；写清第一版必须有 / 后续版本 / 明确不做三组，不做的写原因和重新评估时间
4. 与 AI 讨论：项目类型、目标用户、核心问题、第一版边界、长期规划
5. 让 AI 查漏补缺：权限、数据结构、状态字段、后期扩展、合规风险
6. 生成立项文档（按 PRD 五段结构：背景目标 / 方案概述 / 具体方案 / 上线计划 / 附录；覆盖 10 项：立项说明、用户证据、功能边界、Out-of-Scope、用户路径、业务对象、技术路线、风险清单、里程碑、验收规则）
7. **功能清单分解**（三维度：按角色 / 按业务流程 / 按模块）
   - 每个功能写清：给谁用、输入、输出、权限、正常流程、异常边界
   - 复杂功能（订单流转 / 支付退款 / 优惠叠加 / 权限系统）单独建立文档 + 留索引
8. **阶段计划制定**
   - 第一阶段必须是 MVP（能跑通核心流程的最小可用版本）
   - 只给大阶段划分，不细化到技术实现（等选型定了再排细节）
9. **文档组织检查**
   - 一份文档只做一件事（立项 / 选型 / 宪法不混在一份里）
   - 文档之间引用关系清楚（功能清单 ← 立项文档，阶段计划 ← 功能清单）
   - 复杂功能从功能清单索引出去（单独文档 + 清单里留索引）
10. 提交 Git：`git commit -m "chore: 完成项目立项"`

### 完成判定
- [ ] 项目文件夹存在且命名规范
- [ ] 至少有 3 条真实用户证据，假设已单独标注
- [ ] 立项文档已生成，按 PRD 五段结构覆盖 10 项内容
- [ ] Out-of-Scope 清单已写明（不做 + 原因 + 重新评估时间）
- [ ] 风险清单已列出（需求 / 技术 / 合规 / 上线）
- [ ] 功能清单已分解（三维度完整，复杂功能已单独建立文档）
- [ ] 阶段计划已制定（第一阶段是 MVP，只给大方向）
- [ ] 文档组织合规（一份文档只做一件事，引用关系清楚）
- [ ] AI 已确认"暂时不要写代码"
- [ ] 已提交 Git

### 反模式
- ❌ 直接说"帮我做个项目"
- ❌ 跳过讨论直接让 AI 创建文件、安装依赖
- ❌ 立项文档只在对话里聊过，没有写入文件
- ❌ **把朋友夸奖、假设性回答当成用户证据**（没有具体行为的描述不算证据）
- ❌ **立项文档没有 Out-of-Scope**（第一版边界无限膨胀）
- ❌ **没有风险清单**（需求 / 技术 / 合规 / 上线风险没数）
- ❌ **跳过功能清单直接写代码**（AI 自由脑补边界）
- ❌ **功能清单只按模块划分，漏了角色和业务流程维度**
- ❌ **复杂功能硬塞进功能清单**（应单独建立文档 + 留索引）
- ❌ **没做阶段计划就开始写代码**（不知道先做什么，MVP 跑不通）
- ❌ **阶段计划直接细化到技术实现**（选型没定排细节 = 白排）
- ❌ **一份文档塞多件事**（立项文档里混着技术选型 + 宪法）
- ❌ **文档之间没有引用关系**（功能清单 / 阶段计划 / 复杂功能文档像散沙）

## 02 技术选型

**触发条件**：立项文档已生成，准备进入开发
**输入**：立项文档 + 部署要求 + 维护能力
**输出**：技术选型文档 + 运行环境确认表

### 核心步骤
1. 确定产品形态（网站 / 小程序 / App / 后台 / 纯后端）
2. 让 AI 给"唯一推荐技术方案"（不要列多个方案）
3. 优先选成熟框架和 SDK（查 GitHub star、issue 活跃度、最近提交时间、许可证）
4. 给 AI 画边界（必须遵守当前框架官方规范）
5. **确认运行环境与工具**：运行时版本、包管理器、数据库版本、启动命令、环境变量、部署方式；让 AI 复述一遍从零安装步骤
6. 写进技术选型文档（产品形态、前端、后端、数据库、框架 SDK 列表、选的理由、不选的理由、重评估条件、运行环境版本）
7. 建 `.env.example`（写清每个变量填什么，不放真值）和 README（安装 / 启动 / 构建命令），按 README 能从零跑起来
8. 提交 Git：`git commit -m "chore: 确定项目技术方案"`

### 完成判定
- [ ] 产品形态已确定
- [ ] AI 给出唯一推荐方案并说明理由
- [ ] 框架/SDK 成熟度已核查
- [ ] 技术选型文档已生成，写明运行时与数据库版本
- [ ] `.env.example` 和 README 已建立，按 README 能复现环境
- [ ] 已提交 Git

### 反模式
- ❌ 让 AI 列三四套方案让你选
- ❌ 为了看起来高级选资料少、AI 不熟的方案
- ❌ 技术方案只在对话里聊过没写进文档
- ❌ 没写运行时版本和包管理器（换台机器就跑不起来）
- ❌ 只有代码没有 README 和 `.env.example`（新人不知道变量填什么）

## 03 架构设计文档

**触发条件**：技术选型已确定
**输入**：立项文档 + 技术选型文档
**输出**：架构设计文档（目录结构 + 接口规则 + 错误处理 + 日志规则等）

### 核心步骤
1. 让 AI 输出《项目架构设计文档》草稿，包含：
   - 目录结构规则（每个目录职责 / 放什么 / 不放什么）
   - 接口响应规则（统一格式 / 错误码表 / 分页规则）
   - 错误处理规则（异常捕获 / 日志记录 / 返回格式）
   - 日志规则（级别 / 格式 / 关键操作清单）
   - 数据库连接规则（连接池 / 事务边界 / ORM 使用规范）
   - 权限入口（认证中间件 / 角色校验 / 数据归属校验位置）
   - 框架复用边界（必须用框架 / 可封装 / 禁止自造）
   - 新增模块规则（一个新模块要改哪些地方）
2. 先列大纲让用户确认，确认后再写完整版
3. 写入 `docs/e-架构设计文档.md`
4. 提交 Git：`git commit -m "chore: 完成架构设计文档"`

### 完成判定
- [ ] 架构设计文档已写入 `docs/e-架构设计文档.md`
- [ ] 目录结构规则清晰（每个目录职责明确）
- [ ] 接口响应规则（统一格式 + 错误码表 + 分页规则）
- [ ] 错误处理规则（异常捕获 / 日志 / 返回）
- [ ] 框架复用边界清楚（必须用框架 / 可封装 / 禁止自造）
- [ ] 已提交 Git

### 反模式
- ❌ 跳过架构设计文档直接写宪法或代码
- ❌ 把长期原则塞进架构设计文档（那是宪法的职责）
- ❌ 把具体技术细节塞进宪法（应放架构设计文档 / 真源文档）

## 04 Agent 宪法（一点点攒）

**触发条件**：架构设计文档已完成
**输入**：立项文档 + 技术选型文档 + 架构设计文档
**输出**：Agent 宪法文件（基础版）

### 核心步骤
1. 确定宪法文件位置（Codex: `AGENTS.md` / Cursor: `.cursor/rules/` / Claude Code: `CLAUDE.md` / Trae: `.trae/rules/project.md`）
2. 遵守三条写作原则：短硬清楚、写长期原则、写禁止事项和验收标准
3. 写可执行、可检查、可判断的规则（不要写"认真一点""写好一点"）
4. 套用模板（安全诚信、诚实边界、执行铁律、代码生成器承诺）
5. 项目专属条款（基于立项 + 选型 + 架构设计文档的真实情况追加）
6. **这是基础版，后续每踩一个坑、每定一个规则，就往宪法里加一条**
7. 提交 Git：`git commit -m "chore: 创建项目 Agent 宪法（基础版）"`

### 完成判定
- [ ] 宪法文件放在 IDE 会读取的位置
- [ ] 主体不超过 200 行
- [ ] 包含禁止事项（≥ 5 条）和验收标准
- [ ] 含框架优先原则
- [ ] 项目专属条款已追加（≥ 5 条）
- [ ] 各 IDE 入口文件已创建并引用宪法（不复制内容）
- [ ] 已提交 Git

### 反模式
- ❌ 试图一次性写完所有规则（应该一点点攒）
- ❌ 把项目介绍、技术细节、部署流程全塞进宪法
- ❌ 写"注意质量""认真一点"这种模糊口号
- ❌ 把"具体怎么做"全写进宪法（应放进架构设计文档或真源文档）
- ❌ 入口文件复制宪法内容（多处会不同步）

## 05 实施真源文档分解

**触发条件**：Agent 宪法基础版已创建
**输入**：立项文档 + 功能清单 + 阶段计划 + Agent 宪法
**输出**：实施真源文档（首个大阶段）

### 核心步骤
1. 让 AI 把**首个大阶段**分解成实施真源文档：
   - 大阶段名称和目标
   - 子阶段划分（每个子阶段的目标）
   - 每个子阶段的步骤（每步做什么）
   - 每步的验收标准（怎么算做完）
2. 三大核心：**明确执行目标、划定任务边界、制定验收标准**
3. 不是越细越好——能说清目标、边界、验收就行
4. 先只分解首个阶段，后续完成后再分解下一个（避免一次性太细导致后续大幅修改）
5. 写入 `docs/f-实施真源文档-第N阶段.md`
6. 提交 Git：`git commit -m "chore: 完成首阶段实施真源文档分解"`

### 任务分解原则
- 完成首个阶段，然后分解后续阶段，不需要一次性太细
- 业务细节可以随手调整，但地基（底层架构）不能随手翻
- 能改的只是和底层架构无关的需求
- 判断不了就直接问 AI 讨论
- 临时想法先写回真源文档，不要直接改代码

### 完成判定
- [ ] 首个阶段的实施真源文档已写入 `docs/f-实施真源文档-第N阶段.md`
- [ ] 大阶段 → 子阶段 → 步骤清晰
- [ ] 每步有验收标准
- [ ] 已提交 Git

### 反模式
- ❌ 一次性把所有阶段都分解完（应该完成一个分解一个）
- ❌ 分解得太细（能说清目标、边界、验收就行）
- ❌ 没有验收标准（分解了等于没分解）
- ❌ 临时想法直接改代码不写回真源文档

## 06 前端骨架搭建

**触发条件**：立项、技术选型、架构设计文档、宪法、实施真源文档都已完成
**输入**：立项文档 + 技术选型文档 + 架构设计文档 + Agent 宪法
**输出**：前端架构实施文档 + 最小可运行骨架
**参考库**：`references/UIUX参考库索引.md` 的「阶段 6」一行指向 `DESIGN_SYSTEM.md` §1–§8、§10、§11、`projects.html`、`patterns.html`；先读参考库的 `AI-CONTEXT.md`，再取 token、组件、页面状态与页面套路

### 核心步骤
1. 确定整体设计风格（玻璃拟态 / Material / 企业级 / SaaS 极简 / AI 科技感），给 2-3 个参考案例并说明参考的是排版、配色还是信息密度
2. 确定前端技术方案和 UI 组件库（不要混：技术方案管结构，UI 库管界面）
3. 给 AI 画边界（必须遵守前端框架官方规范，优先复用 UI 组件库）
4. 定目录、模块、组件规则（目录边界、模块边界、组件复用规则）
5. 准备样式系统（设计 token 具体值、响应式断点、页面状态、可访问性底线、多语言规范、主题规则）
6. 写进前端架构实施文档（风格方向、技术方案、UI 库、布局、响应式、页面状态、可访问性、目录结构、模块边界、组件封装、token、多语言、主题、AI 使用规则、第一阶段内容、验收标准）
7. 搭最小可运行骨架（能启动、首页能打开、路由清楚、目录规范、UI 库接入、token 已生效、主题接入、一个示例页面展示加载 / 空 / 错误三种状态）
8. 验收 + 提交 Git：`git commit -m "feat: 搭建前端最小可运行骨架"`

### 完成判定
- [ ] 设计风格已明确，有参考案例
- [ ] 设计规范已写入实施文档（风格方向 / token 具体值 / 断点 / 页面状态 / 可访问性 / AI 规则）
- [ ] 设计 token 已定义并生效（颜色 / 字号 / 间距 / 圆角 / 阴影 / 断点）
- [ ] 页面样式只用 token（没有零散的十六进制颜色和随手取的字号）
- [ ] 前端框架 + UI 组件库已接入
- [ ] 目录/模块/组件规则已写进实施文档
- [ ] 路由结构搭好
- [ ] 接口层封装完成
- [ ] 响应式断点已定，移动端能正常打开
- [ ] 加载 / 空 / 错误状态各有一个示例
- [ ] 键盘可操作，交互元素有聚焦样式
- [ ] 项目能启动、首页能打开
- [ ] 已提交 Git

### 反模式
- ❌ 直接让 AI 写页面，跳过骨架
- ❌ 一次性做完所有页面和功能
- ❌ 没有 UI 组件库，让 AI 到处手写按钮/弹窗/表格
- ❌ 设计 token 没提前定，到处写十六进制颜色和随手取的字号
- ❌ 只做桌面端，移动端打开就错位
- ❌ 只写正常状态，没有加载 / 空 / 错误状态
- ❌ 只靠鼠标能操作，键盘聚焦看不见

## 07 数据库设计

**触发条件**：前端骨架已搭好
**输入**：前端页面列表 + 立项文档里的业务对象清单 + 架构设计文档
**输出**：数据库设计文件（schema.sql 或 migration）+ 数据库实施计划

### 核心步骤
1. 从前端反推数据（页面列表 → 数据字段、详情页 → 完整结构、表单 → 提交数据、按钮 → 操作行为、状态 → 数据流转）
2. 从业务流程里找对象（电商：用户/商品/订单；内容：用户/文章/评论；后台：用户/角色/权限）
3. 确认对象之间的关系（一对一、一对多、多对多、关联字段在哪）
4. 确定数据库服务（主数据库用 MySQL 或 PostgreSQL，要不要 Redis）
5. 设计表结构和字段规范（三大范式：字段原子化、围绕主对象、不互相依赖）
6. 规范常见字段（id、created_at、updated_at、deleted_at、password_hash、金额用精确类型、状态字段枚举值、字段名英文下划线）
7. **设计索引**（按高频查询建：外键、状态、时间；写清索引名、字段顺序、对应查询语句；不要给每一列都建索引）
8. **设计事务与迁移**（每个多表写入场景的事务起止、隔离级别、失败回滚方式；每条 migration 写前进步骤和回退步骤；先备份再执行）
9. **设计连接池、数据隔离、备份**（最大连接数 / 获取超时 / 空闲回收与数据库上限匹配；查询条件必须带租户或用户标识；备份频率、保留天数、恢复演练记录）
10. **先生成设计文件，再建表**（禁止直接连数据库建表）
11. 写进实施计划（业务对象、对象关系、主数据库、Redis、核心表、字段规范、表间关联、软删除、范式校验、索引、事务、迁移、连接池、数据隔离、备份、验收标准）
12. 跑通基础结构 + 提交 Git：`git commit -m "feat: 完成数据库设计文件并跑通基础结构"`

### 完成判定
- [ ] 业务对象清单已整理
- [ ] 对象关系已确认（ER 图）
- [ ] 数据库服务已选定
- [ ] 表结构符合三大范式（或反范式有说明）
- [ ] 常见字段规范已确认（金额用 decimal、密码哈希存储、软删除字段一致）
- [ ] 索引已设计并写明对应查询（外键 / 状态 / 时间，没有给每一列都建）
- [ ] 多表写入的事务边界、隔离级别、失败回滚已写明
- [ ] 每条 migration 有前进和回退步骤
- [ ] 连接池参数与数据库上限匹配
- [ ] 数据隔离规则已写（查询带租户 / 用户标识）
- [ ] 备份频率、保留天数、恢复方式已写
- [ ] schema.sql / migration 文件已生成且可独立执行
- [ ] 数据库能连接、能建表、能插入和查询测试数据
- [ ] 建表后有索引证据（SHOW INDEX 输出）
- [ ] 已提交 Git

### 反模式
- ❌ 直接让 AI 连数据库建表，跳过设计文件
- ❌ 所有数据塞进一个大字段
- ❌ 表关系没设计清楚就开建
- ❌ 密码明文存储
- ❌ 金额用浮点数
- ❌ 给每一列都建索引（写入变慢且没有收益）
- ❌ 多表写入不开事务（一半成功一半失败）
- ❌ migration 只写前进不写回退
- ❌ 没有 migration 记录，直接手动改字段
- ❌ 直接在生产库改字段，没有备份

## 11 业务模块开发

**触发条件**：后端架构验收通过
**输入**：实施真源文档 + 后端架构实施真源文档 + Agent 宪法 + 功能清单
**输出**：可运行的业务模块（一个模块一个模块交付）

### 核心步骤

**开发节奏**：一个模块一个模块写接口，边写边接前端，做完一个模块就**测试 → 验收 → 提交 git**。

1. **划分当前轮次任务**：从实施真源文档取当前要做的子阶段，明确本轮做什么
2. **后端写接口**：按后端架构实施真源文档的规则，写当前模块的接口
3. **立即接前端**：后端接口写完，立即接前端页面验证
4. **模块测试**：模块完成后走 `testing-strategy` Skill 测试六步法（手动闭环 → 三类用例 → 回归自动化 → 假测试陷阱 → 安全攻防 → 防过度测试）
5. **模块验收**：测试通过后走 `verification-before-completion` Skill 验收，对照实施真源文档检查
6. **提交 Git**：每完成一个模块就提交一次 `git commit -m "feat: 完成XX模块"`

**执行交付期 prompt**：
```
严格遵守 Agent 宪法和实施真源文档，只实施当前子阶段，不要超出范围，做完后停下来汇报，不要自动进入下一个子阶段。

边写边接前端：后端接口写完，立即接前端页面验证。

完成后汇报三件事：
1. 对照实施真源文档，这个阶段哪些做完了，哪些还没做完
2. 到底改了哪些地方，有没有漏做，有没有多做
3. 怎么验证的，验证结果是什么，下一个该做哪个子阶段，为什么
```

### 完成判定（每个模块）
- [ ] 接口按架构设计文档规则实现
- [ ] 前端已接通并能正常交互
- [ ] 对照实施真源文档，本模块功能完整
- [ ] 验收有证据（请求 / 响应 / 截图）
- [ ] 已提交 Git

### 反模式
- ❌ 一次写多个模块才验收（出问题分不清是哪个模块的）
- ❌ 后端写一堆接口不接前端（接的时候才发现对不上）
- ❌ 超出当前子阶段范围（AI 自动往下做）
- ❌ 做完不汇报，直接进入下一阶段
- ❌ 临时想法直接改代码不写回真源文档
- ❌ 改了规则没同步真源文档

## 12 后端安全审查

**触发条件**：业务模块开发到一定阶段，重要功能上线前
**输入**：后端架构实施真源文档 + 前端架构实施真源文档 + 当前业务功能清单
**输出**：后端安全边界表 + 系统权限设计表 + 认证密钥审查 + 注入风险审查报告 + 安全整改清单 + `docs/o-安全审查报告.md`

### 核心步骤
1. 划定安全边界（5 道关卡：身份认证、权限控制、输入校验、数据归属、注入防护）
2. 审查接口输入（默认不可信，关键输入和普通输入分开处理）
3. 审查密码和管理员账号规则（密码长度、字符组合、弱密码拦截、哈希存储、失败次数限制）
4. 审查认证与密钥生命周期（token 有效期、刷新规则、退出后立即失效、密钥轮换方式；密钥只从环境变量读取，`.env` 进 `.gitignore`）
5. 审查跨域与角色权限（只允许明确列出的来源，不使用通配符，凭证请求配置正确；角色 × 接口矩阵存在，管理员接口单独校验）
6. 审查限流（登录、注册、验证码、发送类接口都有频率上限）
7. 审查日志与生产错误信息（日志脱敏；对外只返回错误码和用户可读信息，不暴露路径、SQL、调用信息）
8. 审查依赖安全（锁定文件已提交，依赖审计命令无已知高危漏洞）
9. 输出系统权限设计表（每个接口：是否需要登录、允许哪些角色、是否只能操作自己的数据、权限判断在哪里、无权限返回什么）
10. 检查注入风险（SQL 注入、命令注入、模板注入，用框架 ORM 还是字符串拼接）
11. 审查过度防御（区分必须校验的业务规则、框架已处理的基础校验、前端体验层处理、无用代码）
12. 整改 + 回归（把所有"未验证"或"风险"项整理成整改清单，逐项修复后重新执行）
13. 审查结果写入 `docs/o-安全审查报告.md`（5 大维度 + 认证密钥 + 跨域 / 角色权限 / 限流 + 生产错误信息 + 依赖审计 + 整改清单 + 安全边界表 + 权限设计表）
14. 提交 Git：`git commit -m "chore: 后端安全审查通过"`

### 完成判定
- [ ] 安全边界表覆盖 5 道关卡，每项有证据
- [ ] 关键输入和普通输入分开处理
- [ ] 密码规则、哈希存储、失败次数限制齐全
- [ ] 水平越权测试通过（用户 A 的 token 调用户 B 的资源返回 403）
- [ ] token 有效期、刷新、退出失效规则已确认
- [ ] 密钥只从环境变量读取，未入库、未进前端代码、未写入日志
- [ ] `.env` 已加入 `.gitignore`
- [ ] 跨域只允许明确列出的来源，凭证请求配置正确
- [ ] 角色 × 接口矩阵存在，管理员接口有单独校验
- [ ] 登录、注册、验证码、发送类接口有限流
- [ ] 生产环境错误信息不暴露路径、SQL、调用信息
- [ ] 依赖审计无已知高危漏洞
- [ ] 系统权限设计表覆盖所有接口
- [ ] 无字符串拼接用户输入的注入风险
- [ ] 无无用代码或过度防御
- [ ] 安全审查报告已写入 `docs/o-安全审查报告.md`
- [ ] 已提交 Git

### 反模式
- ❌ 听 AI 说"已经做了安全处理"就放过
- ❌ 只做"要不要登录"忽略水平越权
- ❌ 让 AI 自己写过滤规则代替参数化查询
- ❌ 密钥硬编码在代码、构建产物或日志里
- ❌ 跨域写成 `*`（等于对所有网站开放）
- ❌ 管理员按钮只在前端隐藏，接口不做角色校验
- ❌ 登录、验证码接口不限流（可被撞库和刷短信）
- ❌ 生产环境把调用信息和 SQL 直接返回给用户
- ❌ 依赖有已知高危漏洞仍然上线
- ❌ 为了安全感堆一堆永远走不到的判断分支

## 13 上线前总验收

**触发条件**：业务模块全部完成，安全审查通过
**输入**：所有阶段的文档 + 代码 + 验收报告
**输出**：上线前验收报告 + 上线检查清单

### 核心步骤
1. 回顾所有门禁是否都通过（立项门 / 架构门 / 业务门）
2. 功能完整性验收（对照功能清单逐项检查）
3. 模块清单核对（已完成 / 需优化 / 可上线 / 阻塞中）
4. 文档完整性检查（立项 / 选型 / 架构设计 / 宪法 / 真源文档 / 验收报告齐全）
5. **5 维度系统审查**（结构：目录 / 分层 / 重复实现；规则：宪法 / 真源文档 / 框架规范；安全：输入校验 / 越权 / 认证 / 密钥 / 跨域 / 限流；数据：schema / migration / 敏感数据 / 索引 / 事务；可维护性：命名 / 硬编码 / 日志 / 错误 / 测试），每项给"通过 / 风险 / 严重"+ 证据
6. **上线准备核对**（生产构建 / 环境变量 / 数据库迁移 / 迁移前备份 / 静态资源 / 域名 / HTTPS 证书）
7. **部署条件核对**（健康检查 / 监控与告警 / 回滚步骤演练）
8. **对外能力核对**（页面 title 和 description / canonical / sitemap / robots / 分享卡片 / 访问统计与关键事件 / 隐私政策 / 用户协议 / 备案）
9. 墓碑代码专项体检（临时测试 / 调试打印 / 临时测试接口 / 硬编码假数据 / 一次性脚本；先列清单 → 用户确认 → 再删；无权限校验的临时接口与硬编码假数据单独标出；勿删正式回归测试与有意保留的运行日志）
10. 风险分级 + 整改清单（🔴 严重：阻断上线 / 🟡 风险：可上线后修 / 🟢 建议：可选优化）
11. 上线决策（哪些模块足够上线，哪些需要优化后再上线）
12. 报告写入 `docs/p-上线前验收报告.md`（5 维度 + 风险分级 + 整改清单 + 上线建议）
13. 提交 Git：`git commit -m "chore: 上线前总验收通过"`

### 完成判定
- [ ] 所有门禁已通过
- [ ] 功能清单逐项核对完成
- [ ] 模块清单状态明确（可上线 / 需优化 / 阻塞中）
- [ ] 文档齐全
- [ ] 5 维度审查完成，无 🔴 严重项
- [ ] 🟡 风险项已登记后期清单
- [ ] 上线检查清单逐项完成（构建 / 环境变量 / 迁移 / 域名 / HTTPS / 冒烟 / 监控 / 回滚）
- [ ] 监控与告警已配置，回滚步骤已演练
- [ ] SEO 基础项与分享卡片已完成（对外站点）
- [ ] 访问统计已接入，关键事件已记录
- [ ] 隐私政策 / 用户协议 / 备案已确认（如适用）
- [ ] 墓碑代码已清理（先清单后删，勿删回归测试 / 运行日志）
- [ ] 上线前验收报告已写入 `docs/p-上线前验收报告.md`
- [ ] 上线决策已做
- [ ] 已提交 Git

### 反模式
- ❌ 没做总验收直接上线
- ❌ 模块状态不清就上线（哪些能上哪些不能上没数）
- ❌ 文档零散没整理，上线后接手困难
- ❌ 没做冒烟测试就宣布可上线
- ❌ 环境变量和密钥跟着构建产物一起发布
- ❌ 数据库迁移只在本地跑过
- ❌ 没有备份就执行迁移
- ❌ 没演练回滚（出事不知道从哪退回）
- ❌ 没有监控和告警（上线后出问题只能靠用户反馈）
- ❌ 页面没有 title 和 description（搜索结果里显示空白）
- ❌ 没有访问统计和关键事件（不知道用户从哪来、卡在哪一步）
- ❌ 没有隐私政策和用户协议
- ❌ 需要备案却没备案就上线

## 14 上线 + Skill 反哺

**触发条件**：上线前总验收通过
**输入**：项目所有产出
**输出**：已上线系统 + 发布记录 + 项目复盘报告 + 30 天迭代计划 + Skill 库更新

### 核心步骤
1. **部署上线**（按上线检查清单逐项执行：生产构建 → 配置环境变量 → 数据库迁移并验证 → 备份 → 发布 → 域名与证书）
2. **冒烟测试**（按核心用户流程实际走一遍，每步给请求 + 响应 + 是否通过）
3. **检查日志与监控**（日志能查到本次请求，监控面板有数据，告警规则已配置并有测试告警）
4. **回滚演练**（实际执行一次回滚，回滚后再次冒烟测试，确认可用）
5. **填发布记录**（访问地址 / 部署平台 / 版本 / 部署时间 / 部署命令 / 回滚命令 / 监控地址 / 统计地址）
6. **整理踩坑清单**（从 PROJECT_STATUS.md 的「踩坑记录」提取）
7. **反哺 skills/**
   - 哪个 Skill 没覆盖到这次的坑？→ 加规则
   - 哪个 Skill 的规则不够强？→ 强化
8. **反哺 Prompt 模板库**（哪个 prompt 不好用 → 改进，缺哪个 → 新增）
9. **写复盘报告** `docs/q-项目复盘报告.md`（上线记录 / 上线后指标基线 / 踩坑清单 / Skill 改进清单 / Prompt 改进清单 / 下次项目提醒）
   - 每条新增规则标注来源：`[日期] 规则描述 — 来源：XX项目XX阶段XX问题`
10. **更新 PROJECT_STATUS.md**（上线信息 + 指标基线 + 下次项目提醒）
11. **建 30 天迭代计划** `docs/r-上线后30天迭代计划.md`，按 24 小时 / 第 1 周 / 每周 / 第 30 天四个节点跟踪
12. **知识库 Git 提交**：
   ```
   cd <知识库根目录>
   git add skills/ docs/ templates/ workflows/
   git commit -m "docs: 反哺 N 条新经验到知识库"
   git push
   ```

### 上线后 30 天循环

| 时间 | 要做什么 | 产出 |
|---|---|---|
| 上线 24 小时 | 看错误率、响应时间、核心流程是否可用 | 24 小时观察记录 |
| 第 1 周 | 登记全部用户反馈，按缺陷 / 体验 / 功能缺失 / 误解 / 价格归类 | 反馈清单 |
| 第 1 周 | 用 RICE 排序，选 1-3 个本周要验证的假设 | 本周迭代计划 |
| 每周 | 小步发布，灰度验证，出问题按回滚步骤退 | 发布记录 + 指标对比 |
| 第 30 天 | 对比基线，判断哪些假设成立、哪些需求放弃 | 30 天复盘 + Skill 反哺 |

指标基线至少 5 个：访问量、注册量、激活量、核心动作完成量（下单 / 支付 / 提交）、留存。

### 完成判定
- [ ] 项目已上线，生产地址可访问
- [ ] 生产环境冒烟测试通过（核心流程跑通）
- [ ] 日志能查到本次请求，监控面板有数据
- [ ] 告警规则已配置并有测试告警
- [ ] 回滚步骤已实际演练
- [ ] 上线检查清单逐项完成
- [ ] 发布记录已填写（版本号 + 部署命令 + 回滚命令）
- [ ] 复盘报告已写入 `docs/q-项目复盘报告.md`
- [ ] 上线后指标基线已记录（至少 5 个）
- [ ] 30 天迭代计划已建立 `docs/r-上线后30天迭代计划.md`
- [ ] Skill 库已反哺（至少改 1 条经验）
- [ ] Prompt 模板库已更新（如有改进）
- [ ] 知识库已 Git 提交并推送
- [ ] 下次项目提醒已记录

### 反模式
- ❌ 上线完就结束，不反哺知识库
- ❌ 踩了坑不记录，下次继续踩
- ❌ 复盘报告只写成绩不写问题
- ❌ 没有冒烟测试就宣布上线成功

## Git 提交规范

**提交时机**：每完成一个明确阶段并且能正常运行就提交一次。

**commit message 规范**：
- `chore:` 杂项（立项、选型、配置、文档）
- `feat:` 新功能（骨架、业务模块）
- `fix:` Bug 修复
- `refactor:` 重构
- `docs:` 文档更新
- `test:` 测试

**大改之前先确认存档**：
- 当前有没有稳定存档
- 工作区是否干净
- `git status && git diff` 看清楚再动手

**改坏了就回退**：
```
git status
git diff
git checkout .                  # 丢弃本机未提交改动，执行前确认没有要保留的内容
git reset --hard <commit-id>    # 只用于本机尚未推送的提交
```
已推送的提交用 `git revert <commit-id>` 生成反向提交，不改写公共历史。

**推远程之前先确认文件清单**：
- 仓库私有还是公开
- 有没有真实凭证（.env / 密钥）
- 有没有商业计划 / Agent 宪法 / 真实 case

**分支策略（按项目形态分档）**：

| 场景 | 分支模型 | 说明 |
|---|---|---|
| 单人 solo 项目（默认） | 单分支 `main` | 全程在 main 上提交即可，够用，不折腾 |
| 多人协作 / 多环境 | `main` + `dev` + `feature/*` | `dev` 开发主线；`feature/xxx` 每个功能一个分支，做完合并回 dev；`main` 只收稳定版 |
| 需要版本标记 | 用 `tag` | 上线/里程碑打 `git tag v0.1.0`，回滚和追溯有锚点 |

**什么时候必须切多分支**：超过 1 人协作、有测试/生产环境分离、需要并行开发多个功能。solo 项目别过度设计——单分支足够。

**团队协作 Git（多人时）**：

| 动作 | 做法 | 注意 |
|---|---|---|
| 开分支 | 从 `dev` 拉 `feature/订单列表` | 一个功能一条分支，不要多人共用一条 |
| 提交前自查 | `git status` + `git diff` | 只提交本次相关文件，别把配置和临时文件带进去 |
| 推送与评审 | `git push -u origin feature/订单列表`，开 PR | PR 写清改了什么、怎么验证、影响哪些接口 |
| 代码审查 | 至少 1 人看过再合并 | 看行为和边界（权限 / 错误 / 空值），不只看格式 |
| 解决冲突 | 先把 `dev` 合进当前分支，解决后重跑测试 | 冲突解决完必须重新验证，不能只看能编译 |
| 发布 | 合并到 `main` 后打标签 `git tag -a v1.2.0 -m "发布说明"` | 标签跟着推送：`git push --tags` |
| 回滚 | 优先在部署平台回退到上一个版本；代码层用 `git revert <commit>` | 已推送的历史不要用 `reset --hard` 改写 |

**.gitignore 规范（第一天必须做）**：

- **`git init` 后、第一次 `git add` 前，必须建 `.gitignore`**，否则 node_modules / .env 一进去就污染仓库
- **核心忽略清单**：
  ```
  node_modules/
  dist/
  build/
  .env
  .env.local
  *.log
  __pycache__/
  .DS_Store
  .idea/
  .vscode/
  *.db          # SQLite 本地库
  ```
- **铁律**：真实凭证（`.env` / 密钥 / 证书）绝不进 git；建 `.env.example` 占位，写清"这里该填什么"，不放真值

### 反模式
- ❌ 项目已经乱了才想起来用 Git
- ❌ 改一堆功能才提交一次，分不清每次改了什么
- ❌ 不看 `git status` 直接 `git add .`（容易把 .env / 密钥提交进去）
- ❌ 把商业计划 / Agent 宪法 / 真实 case 跟着代码一起推到开源仓库
