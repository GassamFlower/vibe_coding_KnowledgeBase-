# 门禁卡：立项门

> 包含阶段：立项 + 技术选型 + 架构设计文档 + Agent 宪法  
> 过门禁标准：方向已确定、技术方案定了、架构设计有了、AI 有规矩了

---

## 过门禁标准（必须满足的指标）

- [ ] 立项文档已写入文件，采用 PRD 五段结构
- [ ] 至少有 3 条真实用户证据，假设已标注来源
- [ ] Out-of-Scope 清单已写明，第一版边界清楚
- [ ] 功能清单已分解（三维度：角色 / 业务流程 / 模块）
- [ ] 阶段计划已制定（第一阶段必须是 MVP）
- [ ] 技术选型文档已写入文件，AI 给了唯一推荐，并说明淘汰方案的理由
- [ ] 风险清单已列出（需求 / 技术 / 合规 / 上线）
- [ ] 架构设计文档已写入文件（目录结构 + 接口规则 + 错误处理）
- [ ] Agent 宪法已写入文件（基础条款，一点点攒），放在 IDE 会读取的位置
- [ ] 已 Git 提交（至少 4 次：立项 / 选型 / 架构设计 / 宪法），且项目已建 `.gitignore`

---

## 验收清单

### 需求验证与 PRD
- [ ] 目标用户、使用场景、使用频率写清楚
- [ ] 现有替代方案和不足写清楚
- [ ] 至少 3 条真实用户证据（访谈原话 / 真实行为 / 竞品数据）
- [ ] 朋友夸奖、假设性回答、没有具体行为的描述没有当成证据
- [ ] 每条证据标注来源类型和证据强度
- [ ] 第一版必须有 / 后续版本 / 明确不做三组已分开
- [ ] Out-of-Scope 写了原因和重新评估时间
- [ ] 成功指标有基线、目标值和统计方式
- [ ] PRD 包含背景目标 / 方案概述 / 具体方案 / 上线计划 / 附录
- [ ] AI 复述 PRD 后，目标用户、范围、验收标准没有歧义

### 立项文档
- [ ] 项目是什么 / 面向谁 / 解决什么问题
- [ ] 第一版做什么、不做什么（MVP 边界）
- [ ] 产品流程和用户路径
- [ ] 数据和业务对象清单
- [ ] 技术路线初步判断
- [ ] 风险清单（需求 / 技术 / 合规 / 上线）
- [ ] 验收规则（可检查标准）

### 功能清单
- [ ] 按角色分解（普通用户 / 管理员 / 商家等各自能做什么）
- [ ] 按业务流程分解（核心流程走通：如下单 → 支付 → 发货）
- [ ] 按模块分解（相关功能归到一起：账号 / 商品 / 订单）
- [ ] 每个功能写清：给谁用 / 输入 / 输出 / 权限 / 正常流程 / 异常边界
- [ ] 复杂功能已单独建立文档（订单流转 / 支付退款 / 优惠叠加 / 权限系统）
- [ ] 复杂功能在功能清单里留了索引

### 阶段计划
- [ ] 第一阶段是 MVP（能跑通核心流程的最小可用版本）
- [ ] 每个阶段包含哪些功能已说明
- [ ] 为什么这么排已说明
- [ ] 只给大阶段划分，没细化到技术实现（细节等选型定了再排）

### 文档组织
- [ ] 一份文档只做一件事（立项 / 选型 / 宪法不混在一份里）
- [ ] 文档之间引用关系清楚（功能清单 ← 立项文档，阶段计划 ← 功能清单）
- [ ] 复杂功能从功能清单索引出去（单独文档 + 清单里留索引）
- [ ] 没有把多件事塞进一份文档（如立项文档里混着技术选型）

### 技术选型文档
- [ ] 产品形态已确定
- [ ] 前端 / 后端 / 数据库 / SDK 已确定
- [ ] 为什么选、为什么不选其他方案（至少 3 个淘汰方案）
- [ ] 选型维度已覆盖（部署 / 维护 / 性能 / 生态 / 合规 / 已有技术）
- [ ] 更换技术方案的触发条件已写（什么情况下需要重新评估）

### 架构设计文档
- [ ] 目录结构规则清晰（每个目录职责 / 放什么 / 不放什么）
- [ ] 接口响应规则（统一格式 + 错误码表 + 分页规则）
- [ ] 错误处理规则（异常捕获 / 日志记录 / 返回格式）
- [ ] 日志规则（级别 / 格式 / 关键操作清单）
- [ ] 数据库连接规则（连接池 / 事务边界）
- [ ] 权限入口（认证中间件 / 角色校验 / 数据归属校验位置）
- [ ] 框架复用边界（必须用框架 / 可封装 / 禁止自造）

### Agent 宪法
- [ ] 不超过 200 行
- [ ] 含禁止事项（≥ 5 条）
- [ ] 含验收标准
- [ ] 含框架优先原则
- [ ] 各 IDE 入口文件已创建
- [ ] 含成本/上下文约束（明确忽略 node_modules / dist / build / logs / .git 等无关目录）
- [ ] 含模型分层策略（轻量模型做测试检查、付费主力做核心生成、高端模型做审查）
- [ ] 含会话熔断规则（单会话 ≤ 60 条，超长先 /compact 或开新会话）

## 常用 Prompt（5 个）

### 1. 项目启动（挖掘型）
```
当前阶段：项目立项，只做产品讨论和立项设计，暂时不要写代码。
你的角色：我的产品合伙人。

我想做的是：[一句话描述]
面向用户：[谁]
解决什么问题：[什么]

请按以下方式追问我：
1. 围绕项目类型、目标用户、核心问题逐项深挖
2. 主动指出我没想到的盲区
3. 帮我判断第一版 MVP 该做什么、不该做什么
4. 给唯一推荐，不要列多方案让我选
5. 讨论清楚后告诉我"现在可以写立项文档了"，等我确认再写
```

### 2. 功能清单分解（挖掘型）
```
请根据立项文档输出一份详细的功能清单，请逐个功能说明：
- 这个功能给谁用
- 需要哪些输入
- 产生什么结果
- 涉及哪些角色和权限
- 正常流程是什么
- 有哪些异常和边界情况

分解维度：
1. 按角色分解（普通用户 / 管理员 / 商家各自能做什么）
2. 按业务流程分解（核心流程走通）
3. 按模块分解（相关功能归到一起）

如果某个功能特别复杂（如角色权限系统、订单流转、支付退款、优惠叠加），请把它单独写一份文档，并在功能清单里留一个索引指过去。先不要写代码。
```

### 3. 阶段计划（挖掘型）
```
请根据功能清单，把开发划分为几个大阶段：
- 第一阶段必须是一个能跑通核心流程的最小可用版本（MVP）
- 请说明每个阶段包含哪些功能
- 为什么这么排

先只给大的阶段划分，不要现在就细化到具体技术实现和详细开发计划。
（这个时候还不确定开发框架等细节，等确定了再去规划细节）
```

### 4. 技术选型（挖掘型）
```
这是我的立项文档：[贴文档]
产品形态：[Web / 小程序 / App / 后台]
部署要求：[私有 / 公有 / 本地]
维护能力：[1人 / 小团队 / 中型团队]

请给出唯一推荐技术方案，不要列多个方案。说明：
- 前端 / 后端 / 数据库 / SDK
- 为什么选它们（结合我的项目情况）
- 为什么不选其他常见方案（至少 3 个被淘汰方案）
- 哪些情况才需要重新评估
```

### 5. Agent 宪法（挖掘型）
```
当前阶段：Agent 宪法创建。暂时不要写业务代码。
你的角色：项目架构顾问。

上下文：
- 立项文档：[贴]
- 技术选型文档：[贴]

请帮我起草 AGENT_CONSTITUTION.md。要求：
1. 短：不超过 200 行
2. 硬：每条都是必须遵守的强制规则
3. 清楚：每条能直接判断对错
4. 只写长期原则
5. 必须包含：项目专属条款 / 禁止事项 / 验收标准 / 框架优先原则
6. 必须包含成本与上下文约束：忽略无关目录、模型分层、会话熔断（详见 companion/modules/00-cost-context.md）

先列大纲让我确认，确认后再写完整版。
```

### 6. 需求验证与 PRD（挖掘型）
```
当前阶段：立项前的需求验证。暂时不要写代码，也不要急着给功能清单。
你的角色：产品验证顾问。

我的想法：[一句话]
目标用户：[谁]
我目前掌握的情况：[已有访谈、数据、竞品信息]

请按以下顺序推进：
1. 写出三个基本问题：谁在什么场景遇到什么问题、现在怎么解决、为什么现在值得做
2. 列出还需要向真实用户确认的 5 个问题，只问过去行为，不问未来意愿
3. 标出我现有材料里哪些是真实证据，哪些只是假设
4. 帮我识别虚假信号：朋友夸奖、假设性回答、没有具体代价的描述
5. 给出第一版必须有 / 后续版本 / 明确不做三组范围
6. 按 PRD 五段结构起草立项文档，Out-of-Scope 必须单独列出
7. 最后让 AI 复述目标用户、核心问题、第一版范围和验收标准，检查是否有歧义

先给验证结论和范围，等我确认后再写完整 PRD。
```

## 常见遗漏项

- ⚠️ 立项文档只在对话里聊过，没有写入文件
- ⚠️ 把朋友夸奖、假设性回答当成用户证据
- ⚠️ 只有“用户说想要”，没有真实行为、使用频率和代价
- ⚠️ PRD 里全是形容词，没有可验证的成功指标
- ⚠️ 没有 Out-of-Scope，第一版范围无限扩大
- ⚠️ 风险清单只写技术风险，漏了需求、合规和上线风险
- ⚠️ **跳过功能清单直接写代码**（AI 自由脑补边界，后续越改越乱）
- ⚠️ **功能清单只按模块划分，漏了角色和业务流程维度**（功能不完整）
- ⚠️ **复杂功能硬塞进功能清单**（订单流转 / 支付退款等应单独建立文档 + 留索引）
- ⚠️ **没做阶段计划就开始写代码**（不知道先做什么后做什么，MVP 跑不通）
- ⚠️ **阶段计划直接细化到技术实现**（选型还没定就排细节 = 白排）
- ⚠️ **一份文档塞多件事**（立项文档里混着技术选型 + 宪法，后续改一处全乱）
- ⚠️ **文档之间没有引用关系**（功能清单没引用立项文档，阶段计划没引用功能清单，像散沙）
- ⚠️ MVP 边界没划清，第一版什么都想做
- ⚠️ 技术选型让 AI 列了 3 个方案让你选（必须给唯一推荐）
- ⚠️ 宪法写了"建议""尽量"等软词（必须改成强制规则）
- ⚠️ 宪法超过 200 行（把细则移到真源文档）
- ⚠️ IDE 入口文件复制了宪法内容（应该只写引用）
- ⚠️ 宪法没写成本/上下文约束（忽略目录 + 模型分层 + 会话熔断）—— 上下文会随轮次膨胀，Token 费用飙升，精力也被反复沟通消耗
- ⚠️ 项目没建 `.gitignore`，`.env` / node_modules 进了仓库（首次 `git add .` 前必须建好）
